# Android native alarm research (checked 2026-10-12)

## Official Android behavior

- `AlarmManager.setExactAndAllowWhileIdle()` is Android's user-facing exact-alarm option that can run during Doze; it still depends on the user granting exact-alarm special access on Android 12+ and the OS/device's own power policies. Check `canScheduleExactAlarms()`, explain the need, then open `ACTION_REQUEST_SCHEDULE_EXACT_ALARM`. Fresh installs targeting API 33+ are not pre-granted this permission; Android 14+ especially requires explicit handling. `SCHEDULE_EXACT_ALARM` is user-granted and can be revoked. Source: https://developer.android.com/develop/background-work/services/alarms and https://developer.android.com/about/versions/14/changes/schedule-exact-alarms
- Repeating alarms are inexact from Android 4.4 onward. Use one exact alarm per upcoming medicine-time slot and schedule the next occurrence when it fires. The OS cancels alarms at shutdown; `RECEIVE_BOOT_COMPLETED` and a manifest receiver can re-register them after boot, once the user has launched the app at least once. Source: https://developer.android.com/develop/background-work/services/alarms
- Doze defers normal alarms; allow-while-idle methods are the documented option, but delivery is still governed by OS quotas, battery-saving policies, user revocation, and OEM behavior. Test real devices in Doze. Source: https://developer.android.com/training/monitoring-device-state/doze-standby
- Android 13+ requires `POST_NOTIFICATIONS` runtime permission for ordinary notifications. If declined, an alarm callback can fire but the app cannot show the reminder notification. Request in context and provide an explicit settings path. Source: https://developer.android.com/develop/ui/compose/notifications/notification-permission
- Before first unlock after a reboot, apps normally do not run. Direct Boot needs `directBootAware` components plus device-protected storage; OushodhSathi should not put sensitive medicine data in that store by default. Initial native release will reschedule after boot/user unlock and explain this limitation. Source: https://developer.android.com/privacy-and-security/direct-boot
- Android 15 cancels all pending intents when an app is force-stopped; no app should promise alarms after the user force-stops it from Settings. Source: https://developer.android.com/about/versions/15/behavior-changes-all

Source: https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2404-Readme.md

With a public repository, source and its workflow artifact are visible to anyone with public read access (GitHub's web UI requires sign-in for the documented download flow). The workflow sets `retention-days: 1`. Source: https://docs.github.com/en/actions/managing-workflow-runs/downloading-workflow-artifacts
